# noodle

A timetable and course preference management system for colleges. Students pick their electives, class reps manage the schedule, and everyone sees conflicts in real time.

---

## What it does

Colleges typically have a core timetable plus elective/UWE slots that students need to choose from. Noodle handles the full flow:

**Students** pick a minor program and rank their preferred UWE (elective) courses. The system shows them a personal timetable and flags conflicts between their selections and core courses in real time (green/yellow/red).

**Class Representatives (CRs)** get:

- **Demand** — how many of their batches' students want each UWE, and whether it clashes with the batch timetable.
- **Courses** — a personal watch list: search the timetable by code or name and track any course, with red/yellow clash counts against their batch grid.
- **Timetable** — a drag-and-drop weekly grid of their batches' classes (switch between batches or view them together), with the demanded UWEs and watched courses overlaid. Moves are saved server-side, shared live between CRs, and undoable. A CR can only move classes of the batches they represent.
- **Constraints** — mark a professor unavailable; the grid and the server both refuse drops into blocked slots.
- **Browse batch** — read-only view of any batch's weekly schedule.
- **Notifications** — live, when another CR moves a class that is in their batch, on their watch list, or in their students' UWE demand.

**Super Admins** manage which users are CRs for which batches at `/admin` (an email can be granted CR access before that person has ever signed in) and view demand across all students.

## Tech stack

- **SvelteKit** — full-stack framework (frontend + API routes)
- **Svelte 5** with runes mode
- **Tailwind CSS v4**
- **PostgreSQL** via **Drizzle ORM** (self-hosted)
- **Better Auth** — authentication with Google OAuth
- **TypeScript** throughout

## Setup

### 1. Clone and install

```bash
git clone <repo-url>
cd noodle
npm install
```

### 2. Environment variables

Create a `.env` file:

```env
DATABASE_URL="postgres://user:password@host:port/db-name"
ORIGIN=""                # Base URL, e.g. http://localhost:5173
BETTER_AUTH_SECRET=""    # Random 32+ character string
GOOGLE_CLIENT_ID=""
GOOGLE_CLIENT_SECRET=""
```

### 3. Push the database schema

```bash
npm run db:push
```

### 4. Add the timetable

Drop your timetable XLSX file into `src/lib/data/`. It is parsed **at build time** (see the `timetable` plugin in `vite.config.ts`) and baked into the server bundle, so replacing the sheet means rebuilding/redeploying. Batches are synced from it the first time the admin page loads after each deploy.

### 5. Make yourself an admin

New accounts are students. After signing in once:

```sql
UPDATE "user" SET role = 'super_admin' WHERE email = 'you@example.com';
```

### 6. Run

```bash
npm run dev
```

## Upgrading an existing database

Schema changes that add unique indexes can't go through `db:push` alone if the table already holds duplicates. Run the upgrade once (idempotent), then push:

```bash
npm run db:upgrade   # folds duplicate rows, then creates the unique indexes the schema declares
npm run db:push      # creates the new tables (cr_course, pending_cr)
```

Do this **before** deploying a build that relies on them: saving a move and saving preferences are upserts on those indexes.

## Security model

- Every API route requires sign-in; CR routes require a CR or admin.
- The server trusts nothing about a move except *which slot* and *where to*: the slot must exist in the timetable, the caller must be CR of one of its batches (or an admin), the class length comes from the sheet, and professor constraints are enforced server-side.
- Students can only rank courses the sheet marks open-as-UWE.
- Notifications are generated by the server as part of the move, never on client request.
- Sign-out is a POST that revokes the session row. Writes naming a foreign `Origin` are rejected; responses carry a nonce-based CSP, `X-Frame-Options: DENY`, HSTS on HTTPS.
- The spreadsheet never ships to the browser — only the parsed course list does, to signed-in users.

## Database commands

| Command | Description |
|---|---|
| `npm run db:push` | Push schema changes to the database |
| `npm run db:upgrade` | One-off cleanup + unique indexes for older databases |
| `npm test` | Self-checks for the timetable parsing helpers |
| `npm run db:generate` | Generate migration files |
| `npm run db:studio` | Open Drizzle Studio (visual DB editor) |
| `npm run auth:schema` | Regenerate Better Auth tables |

## Roles

| Role | Access |
|---|---|
| `student` | View timetable, submit and lock preferences |
| `cr` | Everything above + demand, watch list, schedule and constraints for assigned batches |
| `super_admin` | Everything + manage CR assignments, view all demand |

Assigning a batch at `/admin` makes an account a `cr`; removing the last one makes it a `student` again.
